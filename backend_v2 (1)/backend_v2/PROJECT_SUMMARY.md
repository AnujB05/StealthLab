# Project Summary: Workflow Debate Platform

## The Basic Idea

The core thesis: small, cheap language models grounded in a company's own documented workflows can outperform large general models operating without that context. Model scale is not the reliability lever; grounding in company specific data is.

The product built on this thesis has three parts, working together as one loop.

**A knowledge structure.** Two connected graphs. A knowledge graph holding entities, policies, and facts about how a company operates, and a task graph holding the actual decomposed steps of its workflows. Both are bi temporal, meaning every fact tracks both when it was true in the world and when the system learned it, so nothing is ever silently overwritten and the full history stays queryable.

**A debate mechanism.** When a workflow bottleneck is detected (a step that fails too often, costs too much, or takes too long), a panel of heterogeneous AI models, sometimes joined by human employees, debates how to fix it. This is modeled on the classical Nyaya dialectic tradition: Vada is the cooperative default mode where the panel builds toward a shared proposal, Jalpa is an adversarial mode that stress tests a leading candidate, and Nirnaya is the independent adjudication step. This debate mechanism, not the knowledge graph itself, is the actual differentiator. Knowledge graphs and process mining tools already exist from well funded competitors (Celonis and similar). A structured, auditable, multi party debate that resolves into an approved and versioned change does not.

**An evaluation and approval gate.** Every proposed fix passes through an evaluator before a human ever sees it. Layer 1 checks the argument itself: does it commit any of five classical logical fallacies (the hetvabhasa taxonomy), is it grounded in real citations to the knowledge graph, is it constructive rather than pure criticism. Layer 2, where it exists, checks the empirical outcome: does the proposed change actually improve the metrics it claims to, tested with real statistical rigor rather than a single before and after number. Nothing is ever applied automatically. A human approves or rejects every change, and the approval itself is written into the graph as part of its permanent history.

## V0: The Core Loop

The first working version proved the loop end to end on a single seeded demo workflow.

What was built: the ontology (knowledge nodes, task nodes, bi temporal edges, a provenance tag distinguishing company fact from external or generated content), a trace ingestion endpoint, the Vada debate engine with a fixed panel of three heterogeneous models, Layer 1 evaluation, an approval endpoint that writes changes back to the graph by closing the old version and appending a new one (never an in place update), a markdown export of any approved change, and a reusable onboarding script that seeds a workflow from a declarative specification rather than hand written code.

Two real bugs were found and fixed during this phase, both invisible to any test that did not touch a live database. Every JSONB write in the system was pre serializing values in Python and casting them in SQL, a pattern that silently corrupted how the database connection decoded JSON on every later read once a custom type codec was registered. It was found by writing a value, reading it back wrong, and tracing the exact mechanism through several isolated tests before the fix was applied everywhere it appeared. Separately, the logic meant to stop the same bottleneck from opening a second debate only checked for an already open debate, not an already recorded trigger, so a scan running before the first debate had actually opened would create a duplicate.

The execution model, whether this product runs the company's workflows itself or only observes and proposes changes to a separate system, was deliberately left open and still is.

## V1: Visualization, Retrieval, and Real Evaluation

Three additions, one of which remains genuinely blocked.

**Task decomposition visualization.** A new endpoint returns the graph neighborhood around any task, and the frontend renders it as a hand drawn layered diagram rather than pulling in a graph visualization library, since the graphs involved are small and the existing design language was already custom built. The layout algorithm was tested against cyclic graphs specifically, since the underlying traversal can return cycles even though workflows are conceptually acyclic.

**Knowledge retrieval and chat.** The embedding columns and vector index had existed in the schema since the very first version and had never once been used. This phase wired them up: real embeddings generated at seeding time, a hybrid search combining vector similarity and full text search through reciprocal rank fusion (chosen because the two scoring methods live on incomparable scales, so averaging their raw scores would be arbitrary), and a chat endpoint that answers questions grounded only in the retrieved graph content, verifying every citation against the real database rather than trusting the model's claim that it exists.

**Statistical evaluation, Layer 2.** The formal machinery: required sample size calculation, Welch's t test (chosen over the more common Student's t test because it does not assume equal variance between the baseline and the candidate, which matters when a proposed change affects consistency as well as average performance), sequential testing with an O'Brien Fleming alpha spending boundary so that checking results early does not inflate the false positive rate, and Benjamini Hochberg correction across multiple metrics tested at once. Every statistical function was validated against a known correct reference value (scipy's own implementation, a worked textbook example) rather than only checked for whether it ran without error.

Two more bugs surfaced here. The variance calculation used a formula that becomes numerically unstable on near constant data, which is exactly what deterministic replay metrics tend to look like, and was replaced with a stable two pass calculation. Separately, the field meant to report the dollar value of an improvement used a relative percentage change, which is mathematically undefined when the baseline is zero, meaning a workflow that improved from a zero percent success rate to a full success rate would have reported no value at all: the worst possible case for exactly the metric meant to justify pricing.

Only the weakest of three possible evidence tiers is implemented (a model simulating what would have happened, clearly labeled as an opinion rather than a measurement, never as fact). The strongest tier needs a resolved decision on execution ownership. The middle tier needs a kind of data the trace schema does not currently capture at all, since it records what happened, not what the available alternatives were.

What remains queued from this phase: routing simple, already precedented bottlenecks to a cheap specialized model instead of the full debate panel is buildable now. Actually training that specialized model is not, because it requires a volume of real completed and approved debates that does not yet exist, and no amount of API access changes that.

## V2: The Public Platform

The second product, sharing the same underlying graph, debate, and evaluation engine but inverting its trust model. V0 and V1 assumed private, single company data. V2 assumes public, anonymous, and sometimes adversarial input.

**Access control.** Every table gained a visibility flag and an owner. The system currently launches as a fully open shared library by default, with private content supported by the schema but not yet enabled, since enabling it safely requires real user authentication that does not exist yet. The important design choice was making every visibility check flow through a single shared function rather than writing the check separately in each query, specifically because the earlier per tenant isolation in the schema had existed as an unused column for a long time without a single query actually filtering by it. Verified against a deliberately constructed case: a public node reachable only by passing through a private one must not be exposed, since checking only the final result and not the path would still leak its existence.

**Rate limiting and cost governance.** Every endpoint that spends money on model calls now has both a request frequency limit and a rolling spending cap, checked and recorded together so that a burst of simultaneous requests cannot each independently think they are still under the limit. The first version of this check did exactly that under real concurrent load in testing, ten requests all approved against a limit of three, because a database transaction alone does not prevent two connections from reading the same stale count at the same time. It was fixed with an explicit lock and reverified under the same concurrent load.

**Generative task decomposition and its defense.** The actual new capability: a member of the public describes an arbitrary problem in plain language and the system proposes a task breakdown for it, something no earlier version could do at all, since every prior workflow had been authored by a person ahead of time. Because this is the first place in the entire system where untrusted public text flows directly into a model, its defense was designed in from the start rather than added afterward. Prompting the model carefully and scanning input for known attack phrasing both help, but neither is a guarantee, since a sufficiently novel phrasing defeats scanning and a sufficiently persuasive one can defeat instructions. The actual guarantee is structural: a generated proposal is only ever allowed to create brand new nodes and connect them to each other. It cannot modify, delete, or attach to anything that already exists in the graph, no matter what the input says, because that capability is not available to it at all. This was verified by deliberately writing a fully compromised test model that tries to escalate anyway and confirming the structural check still stops it, both at the moment of generation and again at the moment of approval, in case a stored proposal was tampered with in between.

**Applying an approved proposal and the frontend for it.** A public submission that a human approves is written into the graph tagged as publicly generated content, distinct from the company's own documented fact, and a new page lets someone submit a problem and see the proposed breakdown rendered as a diagram before deciding whether to accept it.

What remains entirely unbuilt for this half of the plan: the public facing page where solved problems and their proposed improvements are shown with real metrics and where contributors earn some reward for a better solution. That page needs a real identity system first, since the current placeholder identity is an unverified request header, safe only because nothing is private yet and worthless the moment money or reputation is involved. It also needs a formal defense against a participant who has a direct incentive to make their own proposal look better than it is, which becomes the normal case rather than a rare one once rewards exist. Neither exists yet. A background job queue is also still missing, meaning every debate currently runs synchronously inside a single web request, which was an acceptable simplification for one company's occasional use and is not acceptable under real public traffic.

## Tests Done and Passing

148 automated tests run without any database or network connection, covering the debate engine's convergence and termination logic, the statistical functions against known correct reference values, citation extraction and verification, the capability boundary that contains a hijacked decomposition, and rate limit and cost logic in isolation.

Seven separate scripts run the same code against a real, disposable Postgres database rather than a mock, since several of the bugs already described are specifically the kind that only appear against a real database engine under real conditions. Together they cover: the graph traversal and bi temporal update logic, including confirming that closing an old version of a task and opening a new one correctly rewires every edge that depended on the old one; the debate state machine's transaction and locking behavior; the full loop from a detected bottleneck through to a persisted evaluation result; the difference between a debate that genuinely found nothing wrong and one that silently failed because every model call failed; the access control boundary, including the leak case described above; rate limiting under real concurrency; and applying an approved public proposal, including the two separate escalation attempts described above both being refused.

What has never been tested: a real paid model API. Every test in the project runs against either a scripted response or a small local model, since paid API access was unavailable during development. Local testing proves the plumbing works, meaning a model's response gets correctly parsed and correctly checked. It does not prove that a frontier model's actual reasoning quality is good, and it does not prove that a real model reliably produces output in the exact format the system expects. That is the single most likely thing to need adjustment on first real use.

## Queued, Not Yet Done

From V1: training a small specialized model on real approved outcomes, blocked on accumulating enough of those outcomes to train on, not on anything technical.

From V2: a background job queue so debates do not block a web request; real user authentication; connection pool sizing appropriate for public traffic; load testing the graph traversal at a realistic size, since it has only ever been tested against a handful of rows; the public review and reward page; a real identity and payment system; and a formal defense against a participant with a financial incentive to mislead the panel, needed the moment rewards exist.

Across both versions: the strongest and middle tiers of empirical evaluation, one blocked on the execution ownership decision, the other blocked on a gap in what the trace data currently records; and the first real test against a paid model API.

## Conclusion

The core loop, detecting a bottleneck, debating a fix among heterogeneous models, checking that fix's reasoning and where possible its measured outcome, and only ever changing anything after a human approves it with the full history preserved, is built, and it is built on a foundation that has been tested harder than a first version usually is. Every real bug found in this process was found by deliberately running real code against a real database rather than trusting that mocked tests were sufficient, and several of those bugs (the JSONB corruption, the concurrency race, Layer 2 being fully built yet completely unreachable from the actual API) would not have surfaced any other way.

The public facing half of the plan is real but partial. Its riskiest new capability, letting an anonymous stranger's text generate new structure in the graph, was built with its defense as the first design decision rather than a later patch, and that defense was tested against a deliberately hostile model, not just a well behaved one. Its two largest remaining gaps, a genuine identity and reward system and a background job queue for real public load, are both well understood, both bounded in scope, and neither has been started.

Nothing here has yet been proven against a real frontier model's real output. That is the honest, single largest unknown left, and it is also the cheapest one left to close.
